# T-2.5 — Devolver 409 Conflict cuando se viola el UNIQUE

| Campo | Valor |
|---|---|
| Fase | 2 — API |
| Cubre | RF-05 |
| Depende de | T-2.4 |
| Componente | api (`repositorio/reservas.rs`, `http/error.rs`) |
| Rama sugerida | `dev/fase-2-api` |
| Estado | pendiente |

## Objetivo

Cuando dos peticiones intentan el mismo box/fecha/bloque, exactamente una se guarda y la otra
recibe `409 {"codigo":"bloque_ocupado","mensaje":"Ese bloque acaba de ser tomado"}`.

## Pasos de ejecución

1. En `repositorio::reservas::crear`, mapear `SqliteFailure` con
   `extended_code == SQLITE_CONSTRAINT_UNIQUE` → `ErrorRepositorio::BloqueOcupado`.
2. `ErrorApi::from(ErrorServicio::BloqueOcupado)` → `StatusCode::CONFLICT` + `MENSAJE_BLOQUE_OCUPADO`.
3. Log `warn!` con box/fecha/bloque.
4. Test de concurrencia: lanzar 10 `POST` idénticos en paralelo (`tokio::join!`/`JoinSet`) contra
   el router y verificar 1 × 201 y 9 × 409, y que la tabla tenga 1 fila.

## Patrones y buenas prácticas

- **Nunca** "consultar si existe y luego insertar" (condición de carrera). La base decide.
- Distinguir por código de error de SQLite, no por texto del mensaje (cambia entre versiones).

## Validaciones

- [ ] V1 — Test de concurrencia pasa (1 × 201, 9 × 409, 1 fila).
- [ ] V2 — Cuerpo del 409 exactamente `{"codigo":"bloque_ocupado","mensaje":"Ese bloque acaba de ser tomado"}`.
- [ ] V3 — `api.log` registra un `WARN` por cada 409.
