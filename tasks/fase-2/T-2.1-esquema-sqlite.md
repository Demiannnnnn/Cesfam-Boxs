# T-2.1 — Crear el esquema SQLite con las tablas box y reserva y el UNIQUE

| Campo | Valor |
|---|---|
| Fase | 2 — API |
| Cubre | RF-05, RNF-06 |
| Depende de | T-1.2 |
| Componente | api (`db.rs`) |
| Rama sugerida | `dev/fase-2-api` |
| Estado | pendiente |

## Objetivo

Función `db::abrir(ruta)` y `db::migrar(&Connection)` que dejan la base lista, idempotentes,
con `UNIQUE(box_id, fecha, bloque)` y versión de esquema en `PRAGMA user_version`.

## Contexto

- Esquema exacto: `docs/04-api.md` § Esquema SQLite.
- ADR-003 (UNIQUE), ADR-010 (una conexión).

## Pasos de ejecución

1. `api/src/db.rs`:
   - `pub fn abrir(ruta: &Path) -> Result<Connection, rusqlite::Error>` que aplica
     `PRAGMA foreign_keys = ON; journal_mode = WAL; busy_timeout = 5000;`.
   - `pub fn migrar(conn: &mut Connection) -> Result<(), rusqlite::Error>`: lee `user_version`,
     aplica en una transacción las migraciones con índice mayor y actualiza `user_version`.
   - `const MIGRACIONES: &[&str] = &[ "CREATE TABLE box …; CREATE TABLE reserva …; CREATE INDEX …" ];`
2. Tests con `Connection::open_in_memory()`:
   - migrar dos veces no falla (idempotencia),
   - insertar dos reservas iguales falla con `SQLITE_CONSTRAINT_UNIQUE`,
   - bloque 24 falla por `CHECK`,
   - reserva con `box_id` inexistente falla por `FOREIGN KEY`.

## Patrones y buenas prácticas

- **Migraciones versionadas** con `user_version`: permiten cambios futuros (p. ej. T-0.1) sin
  perder datos. Nunca editar una migración ya publicada; agregar una nueva.
- Restricciones en la base (UNIQUE, CHECK, FK) además de la validación en Rust: defensa en profundidad.

## Validaciones

- [ ] V1 — `cargo test -p gestion-box-api db::` pasa con los 4 casos descritos.
- [ ] V2 — `sqlite3 datos-dev/gestion-box.db ".schema reserva"` muestra `UNIQUE (box_id, fecha, bloque)`.
- [ ] V3 — `sqlite3 datos-dev/gestion-box.db "PRAGMA user_version"` devuelve `1`.
