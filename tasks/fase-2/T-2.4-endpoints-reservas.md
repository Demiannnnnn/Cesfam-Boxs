# T-2.4 — Implementar `GET /reservas`, `POST /reservas` y `DELETE /reservas/{id}`

| Campo | Valor |

| Depende de | T-2.1, T-2.3 |
| Componente | api (`repositorio/reservas.rs`, `servicio.rs`, `http/`) |
| Rama sugerida | `dev/fase-2-api` |
| Estado | pendiente |

## Objetivo

Consultar reservas por día o rango, crear y cancelar reservas.

## Pasos de ejecución

1. **Repositorio** `reservas.rs`: `listar_por_rango(conn, desde, hasta)`, `crear(conn, &NuevaReservaValida)`,
   `eliminar(conn, id) -> Result<(), ErrorRepositorio>` (0 filas → `NoEncontrado`).
2. **Servicio**:
   - `crear_reserva`: verificar que el box exista (`404`) y esté activo (`422 box_inactivo`);
     normalizar funcionario (1..=80) y motivo (≤200, vacío→`None`); fijar `creada_en` con la hora local.
   - `listar_reservas(ConsultaReservas)`: `fecha` **o** `desde`+`hasta` (≤366 días, desde ≤ hasta).
3. **HTTP**: `Query<ConsultaReservas>`; `Json<NuevaReserva>`; `Path<i64>`; códigos 200/201/204.
4. Extractor `Json` propio (o `WithRejection`) para que un JSON malformado responda
   `400 datos_invalidos` con cuerpo `ErrorRespuesta`, no el texto plano por defecto de Axum.
5. Tests en `api/tests/reservas.rs`.

## Patrones y buenas prácticas

- El servicio recibe `NuevaReserva` (ya con `Fecha` y `Bloque` válidos por tipos) y produce un
  `NuevaReservaValida` interno: los repositorios solo aceptan datos ya validados.
- Ordenar el `SELECT` por `fecha, bloque, box_id` para respuestas deterministas.

## Validaciones

- [ ] V1 — `POST /reservas` válido → 201 con `id` y `creada_en`.
- [ ] V2 — `GET /reservas?fecha=…` devuelve la reserva; con otra fecha, `[]`.
- [ ] V3 — `GET /reservas?desde=2026-10-01&hasta=2026-10-31` incluye reservas de ambos extremos.
- [ ] V4 — `GET /reservas` sin parámetros → 400.
- [ ] V5 — `POST` con `funcionario: ""` → 400; con box inactivo → 422; con box inexistente → 404.
- [ ] V6 — `DELETE /reservas/{id}` → 204; repetir → 404.
- [ ] V7 — `POST` con JSON malformado → 400 con cuerpo `{"codigo":"datos_invalidos",…}`.
