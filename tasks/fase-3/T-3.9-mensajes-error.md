## Objetivo

Ningún error técnico llega al usuario: cada caso tiene un mensaje en español que dice qué revisar.

## Contexto

- Catálogo: `docs/05-app.md` § Mensajes de error.

## Pasos de ejecución

1. `errores.rs`: `fn mensaje_para(error: &ErrorCliente, equipo: Option<&str>) -> String`.
   Clasificar `reqwest::Error`: `is_timeout()`/`is_connect()` → servidor apagado; error de DNS
   (texto de la causa contiene "dns"/"resolve" o `io::ErrorKind::NotFound` en la cadena) → nombre
   no resuelto; `Api(e)` → `e.mensaje` (ya en español); resto → genérico.
2. El detalle técnico va al log de la app (`eprintln!`/`log`), nunca a la UI.
3. Tests unitarios para cada variante.

## Validaciones

- [ ] V1 — Tests: cada variante de `ErrorCliente` produce el mensaje del catálogo.
- [ ] V2 — `grep -rni "error:\|failed\|refused" app/src/*.ts` sin textos visibles en inglés.
- [ ] V3 — Prueba de aceptación 5 simulada: detener la API → mensaje "Verifica que {equipo} esté encendido…".
